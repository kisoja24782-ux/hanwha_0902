# ex_0916 개념 정리 (출력 파서)

코드 설명 없이 **이 폴더에서 등장하는 개념**만 정리한 문서다. (코드별 설명은 [ex_0916_정리.md](ex_0916_정리.md) 참고)

## 1. 출력 파서(Output Parser)란

- **출력 파서**: LLM이 내놓은 **자유 형식 텍스트를 프로그램이 쓸 수 있는 구조화된 값**(객체, 딕셔너리, 리스트, 날짜, 열거형 등)으로 변환하는 부품.
- 필요한 이유
  - LLM의 기본 출력은 **사람이 읽기 좋은 문장**이라 특정 항목만 꺼내려면 문자열을 다시 해석해야 한다.
  - 파서를 쓰면 원하는 정보만 **안정적으로 추출**할 수 있어 **후속 처리(저장, 계산, 분기)를 자동화**할 수 있다.
- 파서 없이 쓸 때의 문제: 형식이 매번 달라지고, 정규식·문자열 처리로 억지로 뽑아야 하며, 오류에 취약하다.

## 2. 파서의 두 가지 역할

| 역할 | 설명 |
|---|---|
| **형식 지시문 생성** | 모델에게 "이런 형식으로 답하라"고 알려 줄 **안내문(format instructions)**을 만든다. 프롬프트에 넣어야 한다. |
| **파싱(변환)** | 모델이 돌려준 텍스트를 실제 **데이터 타입으로 변환**한다. 형식이 맞지 않으면 오류를 낸다. |

- 즉, 파서는 **"요청 단계에서 형식을 알려 주고, 응답 단계에서 변환한다"**는 두 단계로 동작한다.
- 지시문을 프롬프트에 넣지 않고 파서만 붙이면, 모델이 자유 형식으로 답해 **파싱이 실패**한다.
- 지시문은 프롬프트의 **부분 변수**로 미리 채워 두는 것이 일반적인 패턴이다.

## 3. 구조 정의 개념

### 3.1 스키마(Schema)

- **스키마**: 데이터가 **어떤 필드를 가지고, 각 필드가 어떤 타입인지** 정한 설계도.
- 파서는 스키마를 JSON 스키마로 바꿔 **모델에게 전달하는 지시문의 재료**로 사용한다.

### 3.2 Pydantic

- **Pydantic**: 파이썬에서 **필드와 타입을 선언하면 자동으로 검증**해 주는 데이터 모델 라이브러리.
- 필드마다 **타입, 필수 여부, 설명(description)**을 정의할 수 있다.
- **설명은 곧 프롬프트다**: 필드 설명이 모델에게 전달되는 지시가 되므로, 모호하게 쓰면 **값이 엉뚱하게 채워진다** (예: "보낸 사람"이 불분명하면 받는 사람이 들어감).
- 결과가 단순 딕셔너리가 아니라 **타입 검증을 거친 객체**여서 필드를 속성처럼 안전하게 쓸 수 있다.

### 3.3 JSON

- **JSON**: 키-값 구조의 텍스트 데이터 형식. 사람과 기계 모두 읽기 쉬워 **LLM 구조화 출력의 표준 형식**이다.
- 모델이 JSON 문자열을 만들면 파서가 이를 **딕셔너리/객체로 변환**한다.
- 모델이 JSON을 **마크다운 코드블록(```)으로 감싸 답하는 경우**가 많아, 파서가 이를 벗겨 내고 처리한다.
- **JSON 강제 모드**: 모델 옵션으로 출력을 유효한 JSON으로 **제한**하는 방법(로컬 모델 등). 다만 필드 이름·구조를 지시대로 지킨다는 보장까지는 없다.

## 4. 구조화 출력의 두 가지 접근

| 접근 | 방식 | 특징 |
|---|---|---|
| **프롬프트 + 파서** | 프롬프트에 형식 지시문을 넣고, 응답 텍스트를 사후에 파싱 | 어떤 모델에서든 사용 가능, 형식 준수는 모델 능력에 의존 |
| **모델 내장 구조화 출력** | 모델에 스키마를 직접 바인딩해 **애초에 구조화된 결과를 반환**하게 함 | 코드가 짧고 안정적, 모델이 이 기능을 지원해야 함 |

- 두 방식 모두 결과의 **정확성(내용이 맞는가)**을 보장하지는 않는다. 형식이 맞아도 값이 틀릴 수 있다.
- 스키마 설명만 주고 별도 지시가 없으면 **필드의 의미를 잘못 해석**할 수 있다.

## 5. 파서 종류별 개념

### 5.1 문자열 파서

- 모델 응답(메시지 객체)에서 **텍스트만 꺼내는** 가장 기본적인 파서. 다른 파서의 **전 단계**로도 쓰인다.

### 5.2 쉼표 구분 리스트 파서

- "값, 값, 값" 형태의 답을 **리스트로 분리**한다.
- 지시문이 매우 단순하다 (스키마 없이 "쉼표로 구분해서 답하라").
- **스트리밍의 한계**: 항목이 완성될 때마다 **조각난 리스트**가 나와 활용도가 떨어진다. 전체 리스트가 필요하면 한 번에 받는다.
- 파서는 **쉼표로 자르기만** 하므로, 모델 출력이 깨지면 결과도 깨진다.

### 5.3 구조화 출력 파서 (키-값 딕셔너리)

- 응답 스키마(이름+설명)로 필드를 정의해 **딕셔너리**로 받는다. Pydantic 클래스 없이 **가볍게** 쓸 수 있다.
- 값이 모두 **문자열**이고 타입 검증이 약하다.
- **소형/로컬 모델에서도 형식을 비교적 잘 맞추도록** 돕는 용도. 이런 모델에서는 **필드 설명을 영어로** 쓰는 것이 안정적이다.
- 모델이 만들어 낸 **출처(URL 등)는 환각일 수 있어** 실제 존재 여부를 확인해야 한다.

### 5.4 JSON 파서

- 지정한 스키마에 맞는 **JSON을 딕셔너리로** 돌려준다. 스키마는 **지시문 생성용**이며 결과는 **검증된 객체가 아니라 딕셔너리**다.
- 지시문에는 "JSON 값만 반환, 코드펜스·설명문 금지" 같은 **엄격한 출력 규칙**이 포함된다.
- 원하는 JSON을 안정적으로 만들려면 **모델 용량이 충분히 커야** 하고, 작은 모델은 오류가 잦다.

### 5.5 Pydantic 파서

- 스키마를 Pydantic으로 정의하고, 결과를 **검증된 객체**로 받는다. 타입·필수 필드가 **강하게 검증**된다.
- **딕셔너리 결과(구조화·JSON 파서)와 객체 결과(Pydantic 파서)**의 차이: 접근 방식(키 vs 속성)과 **검증 강도**가 다르다.
- 스키마가 명확하고 **데이터 무결성이 중요한** 경우에 적합하다.

### 5.6 Pandas 데이터프레임 파서

- **자연어 질문을 데이터프레임 연산 명령으로 번역**하고, 그 명령을 **실제 데이터에 실행**한 결과를 돌려준다.
- 모델은 정해진 **명령 문법**(연산:대상[범위])으로만 답해야 하며, **사용 가능한 컬럼 목록**이 지시문에 자동 포함된다.
- 없는 컬럼이나 잘못된 연산이면 **오류 사유를 문장으로** 답하도록 유도한다.
- **결측치(NaN)**: 데이터에 값이 비어 있는 상태. 조회 결과에 그대로 나타난다.
- 결과 검증: 파서가 준 집계값(평균 등)을 **직접 계산한 값과 대조**해 확인할 수 있다.
- 지시문이 영어이고 **연산 이름이 정확히 맞아야** 하므로 질문도 영어로 쓰는 편이 안정적이다.
- **전처리 단계 삽입 개념**: 모델이 답에 **불필요한 따옴표를 붙이면** 파서가 문법을 해석하지 못한다. 이런 문제는 모델과 파서 사이에 **정리(전처리) 단계**를 끼워 해결한다.

### 5.7 날짜 파서

- 모델의 답을 **날짜/시간 객체**로 변환한다. 날짜 계산, 형식 변경 등이 바로 가능하다.
- **날짜 형식 코드**로 형식을 지정한다 (연-월-일 등). 지시문에는 형식과 **예시 날짜**가 자동으로 포함된다.
- 날짜를 그냥 문자열로 받으면 **표기가 실행마다 달라지거나** 모델이 없는 연도를 지어낼 수 있다. 날짜 전용 파서는 이런 **형식 불일치**를 막아 준다.

### 5.8 열거형(Enum) 파서

- **열거형(Enum)**: 미리 정해 둔 **후보 값들의 집합** (예: 빨강/초록/파랑).
- 모델의 답을 **후보 중 하나**로만 받는다. 후보 밖의 답이 나오면 **파싱 오류**가 나서 결과 범위가 보장된다.
- 대표 용도는 **분류(classification)**: 감정, 카테고리, 우선순위 등을 정해진 값으로 받아 이후 코드에서 **안전하게 분기**할 수 있다.
- 모델의 답은 열거형의 **이름이 아닌 값**과 매칭되며, 결과는 열거형 멤버로 돌려받는다.

## 6. 파서를 체인에 넣는 개념

- 파서는 체인의 **마지막 단계**로 붙어 모델 출력을 변환한다: **프롬프트(+형식 지시문) → 모델 → 파서**.
- 파서 앞에 **전처리 단계**를 둘 수 있다 (문자열 추출 → 정리 → 파싱).
- **파서마다 결과 타입이 다르다**: 문자열 / 리스트 / 딕셔너리 / 객체 / 날짜 / 열거형 멤버. 이후 코드는 결과 타입에 맞춰 작성한다.

## 7. 신뢰성 관련 개념

- **형식 오류**: 모델이 지시를 어겨 JSON이 깨지거나 필드가 빠지는 문제. 모델이 클수록, 지시문이 명확할수록 줄어든다.
- **환각(Hallucination)**: 모델이 **사실이 아닌 값을 그럴듯하게 만들어 내는 것**. 출처·날짜·연도 등에서 자주 나타난다.
- **모호한 필드 설명**은 값의 오류로 이어진다 → 설명을 **구체적**으로 쓴다.
- **형식이 맞다고 내용이 맞는 것은 아니다.** 파서는 형식을 보장할 뿐, 사실 여부는 **사람이 검증**해야 한다.
- **기본 모델**(구형)은 형식 준수가 불안정해 결과가 깨질 수 있으므로, 사용할 모델을 **명시**하고 temperature를 **낮게** 둔다.

## 8. 라이브러리 구성 개념

- LangChain은 버전이 올라가며 **핵심 기능(core)**과 **예전 방식의 기능(classic)**, **외부 연동(community 등)**으로 **패키지가 분리**되었다.
- 일부 파서(구조화·Pandas·날짜·열거형)는 **classic 패키지**에서 가져와야 한다. 파서를 못 찾으면 **가져오는 경로(패키지)**부터 확인한다.

## 9. 개념 한눈에 비교

| 파서 | 결과 | 검증 강도 | 적합한 상황 |
|---|---|---|---|
| 문자열 | 문자열 | - | 텍스트만 필요 |
| 쉼표 리스트 | 리스트 | 없음 | 간단한 항목 나열 |
| 구조화(응답 스키마) | 딕셔너리 | 약함 | 키-값 몇 개를 가볍게 |
| JSON | 딕셔너리 | 약함 | JSON 구조 필요, 객체까지는 불필요 |
| Pydantic | 객체 | **강함** | 스키마 명확, 타입 검증 필요 |
| 모델 내장 구조화 출력 | 객체 | 강함 | 최신 모델, 가장 간결 |
| Pandas | 딕셔너리(값·시리즈) | 컬럼·연산 검증 | 자연어로 표 데이터 조회·집계 |
| 날짜 | 날짜 객체 | 형식 검증 | 날짜·시간 추출 |
| 열거형 | 열거형 멤버 | 후보 밖이면 오류 | 정해진 범주로 분류 |

## 10. 핵심 요약

1. 출력 파서는 LLM의 **자유 텍스트를 구조화된 데이터로 바꿔** 후속 처리를 자동화한다.
2. 파서는 **형식 지시문을 만들고(요청), 응답을 변환(응답)**하는 두 역할을 한다. **지시문을 프롬프트에 넣는 것이 필수**다.
3. **스키마의 필드 설명이 곧 프롬프트**이므로 구체적으로 써야 한다.
4. 결과 타입은 **파서마다 다르다** (딕셔너리 / 검증된 객체 / 리스트 / 날짜 / 열거형).
5. 구조화 출력은 **"프롬프트 + 파서"** 방식과 **"모델 내장 구조화 출력"** 방식이 있다.
6. 정해진 값으로 받고 싶으면 **열거형**, 날짜는 **날짜 파서**, 표 데이터 질의는 **Pandas 파서**처럼 목적에 맞는 파서를 고른다.
7. 모델과 파서 사이에 **전처리 단계**를 넣어 모델 출력의 사소한 흠(따옴표 등)을 보정할 수 있다.
8. 파서는 **형식**만 보장한다. 값의 **정확성과 환각 여부는 반드시 별도로 검증**한다.
