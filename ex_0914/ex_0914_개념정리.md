# ex_0914 개념 정리 (LangChain 기초)

코드 설명 없이 **이 폴더에서 등장하는 개념**만 정리한 문서다. (코드별 설명은 [ex_0914_정리.md](ex_0914_정리.md) 참고)

## 1. LLM 애플리케이션의 기본 구조

- **LLM(대규모 언어 모델)**: 입력 텍스트(프롬프트)를 받아 다음에 올 토큰을 예측해 문장을 생성하는 모델. GPT-4o-mini 같은 것이 해당한다.
- **LangChain**: LLM을 직접 호출하는 대신, 프롬프트·모델·출력 처리 같은 부품을 **표준화된 인터페이스**로 만들어 조립할 수 있게 해 주는 프레임워크.
- **챗 모델(Chat Model)**: 문자열 하나가 아니라 **역할이 붙은 메시지 목록**을 입출력으로 쓰는 모델.
- 기본 흐름은 항상 같다: **입력 → 프롬프트 만들기 → 모델 호출 → 결과 가공**.

## 2. 환경 설정과 비밀 정보 관리

- **API 키**: 모델 제공자가 사용자를 식별·과금하는 비밀 값. 유출되면 타인이 내 비용으로 모델을 쓸 수 있다.
- **환경변수**: 키를 코드에 적지 않고 실행 환경에 두는 방식. 라이브러리가 정해진 이름(예: `OPENAI_API_KEY`)의 환경변수를 자동으로 찾아 쓴다.
- **`.env` 파일**: 환경변수를 파일로 모아 두고 프로그램 시작 시 읽어 오는 관례. **버전 관리(Git)에 올리지 않는 것**이 원칙이다.
- 키를 확인할 때도 **일부만 출력**해 노출을 줄인다.
- **가상환경(venv)**: 프로젝트별로 패키지를 분리해 버전 충돌을 막는 독립 파이썬 환경.

## 3. 모델 호출의 기본 개념

### 3.1 호출 방식

| 개념 | 설명 |
|---|---|
| 동기(invoke) | 요청 후 **응답이 끝날 때까지 기다렸다가** 결과를 한 번에 받음 |
| 스트리밍(stream) | 생성되는 **토큰 조각을 도착하는 대로** 받음. 체감 응답 속도가 빠르고 긴 답변에 유리 |

- 스트리밍은 결과가 달라지는 것이 아니라 **전달 방식**만 다르다.
- 스트리밍 객체는 **소비하기 시작할 때** 실제 통신이 일어난다 (지연 실행).

### 3.2 응답 객체의 구성

- **본문(content)**: 실제 답변 텍스트.
- **메타데이터**: 사용한 모델명, 종료 이유(정상 종료/길이 초과 등), 토큰 사용량.
- **토큰 사용량**: 입력(프롬프트) 토큰 + 출력(답변) 토큰 = 총 토큰. **과금과 컨텍스트 한도의 기준**이다.

### 3.3 토큰(Token)

- 모델이 텍스트를 처리하는 **최소 단위**. 단어·글자보다 작을 수도 크기도 하다.
- 한국어는 한 글자가 **여러 바이트 토큰으로 쪼개지기도** 해서 영어보다 토큰이 많이 든다.
- 모델마다 입력·출력 **최대 토큰 수(컨텍스트 윈도우)**가 정해져 있다.

### 3.4 temperature (무작위성)

- 다음 토큰을 고를 때의 **다양성 조절 값**.
- **낮음(0에 가까움)**: 가장 확률 높은 토큰을 주로 선택 → 일관되고 보수적, 재현성 높음.
- **높음**: 확률이 낮은 토큰도 선택 → 창의적이지만 결과가 흔들림.
- 사실 확인·추출·분류 작업은 낮게, 아이디어 생성은 높게 쓰는 것이 일반적이다.

### 3.5 logprob (로그 확률)

- 모델이 **각 토큰을 선택할 때의 확신도**를 로그 확률로 나타낸 값.
- **0에 가까울수록 확신이 높고**, 음수로 클수록 확신이 낮다. (0 → 확률 100%)
- 답변의 **신뢰도 점검, 불확실한 부분 탐지**에 활용할 수 있다.
- 후보 토큰들(top logprobs)을 함께 보려면 별도로 요청해야 한다.

### 3.6 모델 기본값의 함정

- 모델을 **명시하지 않으면 구형 기본 모델**이 쓰일 수 있어 성능·기능(이미지 입력, 도구 호출 등)이 달라진다. 항상 모델 이름을 명시하는 것이 안전하다.

## 4. 메시지와 역할

| 역할 | 의미 |
|---|---|
| **시스템(System)** | 모델의 정체성·규칙·말투를 지시. 대화의 **맨 앞**에 위치 |
| **사용자(Human)** | 사용자의 발화 |
| **AI** | 모델의 이전 답변 (대화 맥락·예시로 활용) |

- 챗 모델은 이 **메시지 목록 전체**를 보고 다음 답변을 만든다.
- **시스템 프롬프트 vs 사용자 프롬프트**: 시스템은 "역할과 규칙"(예: 재무제표를 해석하는 금융 어시스턴트), 사용자는 "이번에 할 구체적 요청".

## 5. 멀티모달(Multimodal)

- **멀티모달**: 텍스트뿐 아니라 **이미지·오디오·비디오** 등 여러 형태의 입력을 함께 다루는 능력.
- 이미지 입력 시 메시지의 내용이 **"텍스트 블록 + 이미지 블록"의 조합**이 된다 (문자열 하나가 아님).
- **이미지를 전달하는 두 가지 방식**
  - **웹 URL**: 모델 서버가 직접 이미지를 내려받는다.
  - **base64 인코딩(data URL)**: 로컬 파일은 서버가 접근할 수 없으므로 이미지 바이트를 **문자열로 변환해 요청에 포함**한다.
- **base64**: 바이너리 데이터를 텍스트 문자로 표현하는 인코딩. 크기가 커지지만 어디서든 전송 가능하다.
- **MIME 타입**: 데이터의 종류를 알려 주는 표기(`image/png`, `image/jpeg`). 인코딩된 이미지가 무슨 형식인지 모델에 알려 준다.
- 활용: 표·재무제표·문서 이미지 해석, 이미지 설명 등.
- **주의**: 이미지 해석 결과도 **환각·오독**이 있을 수 있다 (제목과 내용이 어긋나는 등). 원본과 대조해야 한다.

## 6. 로깅(Logging)

- **로깅**: 프로그램이 실행되는 동안의 **사건을 기록으로 남기는 것**. 문제가 생겼을 때 원인을 추적하는 근거가 된다.
- **로그 레벨**: DEBUG < INFO < WARNING < ERROR < CRITICAL. **설정한 레벨 이상만** 기록된다.
- **로거(Logger)**: 로그의 출처를 구분하는 이름표.
- **핸들러/출력 대상**: 콘솔 또는 파일 중 어디에 기록할지의 설정. 파일로 지정하면 콘솔에는 나오지 않는다.
- **스택 트레이스**: 예외가 어디서 발생했는지 보여 주는 호출 경로. 오류 로그에 **함께 남겨야** 원인을 찾을 수 있다.
- **좋은 로그 배치**: 시작 / **외부 호출 직전(입력값)** / 처리 중간 / 완료. 어디까지 찍혔는지로 실패 지점을 좁힌다.
- **예외 처리(try/except)**: 네트워크·파일처럼 실패할 수 있는 작업을 감싸 오류를 기록하고 프로그램이 죽지 않게 하는 구조.
- 전역 로깅 설정은 **처음 한 번만 적용**되는 성질이 있다.

## 7. 프롬프트 템플릿

- **프롬프트 템플릿**: `{변수}`가 포함된 **재사용 가능한 프롬프트 틀**. 변수 값만 바꿔 여러 입력에 같은 형식의 프롬프트를 만든다.
- 장점: 프롬프트와 데이터의 **분리**, 재사용, 일관성, 변수 누락 검증.
- 변수는 **여러 개** 가능하며, 입력은 변수 이름을 키로 하는 **딕셔너리**로 준다.
- **좋은 프롬프트의 구성 요소**: 역할 부여 → 지시 → 출력 양식(FORMAT) → 입력 변수. 출력 양식을 명시하면 답변 형태가 일정해진다.

## 8. LCEL (LangChain Expression Language)

- **LCEL**: 구성 요소를 **파이프(`|`)로 연결해 체인**을 만드는 선언적 표현 방식.
- 기본 형태: **프롬프트 → 모델 → 출력 파서**. 왼쪽 단계의 출력이 오른쪽 단계의 입력이 된다.
- **Runnable**: LCEL 부품들이 공유하는 **공통 인터페이스**. 모든 Runnable이 같은 실행 메서드(호출/스트리밍/배치/비동기)를 가지므로 **체인 자체도 하나의 Runnable**이 된다.
- 이점: 조립이 간단하고, 스트리밍·배치·비동기가 **자동으로 지원**되며, 추적·디버깅이 쉽다.

## 9. 출력 파서(Output Parser)

- **출력 파서**: 모델의 출력(메시지 객체)을 **다음 단계가 쓰기 좋은 형태로 변환**하는 부품.
- **문자열 출력 파서**: 메시지 객체에서 **텍스트만 꺼내 문자열로** 만든다. 파서가 없으면 결과는 메시지 객체다.
- 체인 끝에 붙이면 스트리밍 결과도 **문자열 조각**으로 바뀐다.
- (구조화된 형태로 변환하는 파서는 ex_0916에서 본격적으로 다룬다.)

## 10. 실행 방식: 단건·일괄·비동기

| 구분 | 동기 | 비동기 |
|---|---|---|
| 단일 입력 → 단일 출력 | invoke | ainvoke |
| 단일 입력 → 스트림 | stream | astream |
| 입력 목록 → 출력 목록 | batch | abatch |
| 중간 단계 로그 스트림 | - | astream_log |

- **배치(batch)**: 여러 입력을 **한 번에** 처리. 결과 목록은 **입력 순서와 동일**하다.
- **동시성 제한(max concurrency)**: 동시에 처리할 요청 수의 상한. 서비스의 **호출 한도(rate limit)** 초과를 막는 데 쓴다.
- **동기 vs 비동기**
  - 동기: 한 작업이 끝나야 다음으로 진행 (대기 시간 동안 멈춤).
  - **비동기**: 응답을 기다리는 동안 **다른 작업을 진행**할 수 있다. 서버·웹 앱처럼 동시에 많은 요청을 다룰 때 유리하다.
- 비동기 호출은 **호출만으로는 실행이 시작되지 않고**, 결과를 기다리는 시점(await)에 실행된다. 주피터에서는 셀 최상단에서 바로 쓸 수 있다.

## 11. Runnable 조합 도구

체인을 **분기·병합·변환**하기 위한 부품들.

| 개념 | 역할 |
|---|---|
| **RunnableParallel** | 같은 입력을 **여러 체인에 동시에 전달**하고, 이름(키)별 결과를 딕셔너리로 묶음. 서로 독립적인 질문 여러 개를 한 번에 처리할 때 사용 |
| **RunnablePassthrough** | 입력을 **그대로 통과**시킴. 입력값을 원하는 키에 매핑하거나, **기존 입력을 유지한 채 새 값을 추가(assign)**할 때 사용 |
| **RunnableLambda** | **일반 함수를 체인 단계**로 사용. 날짜 계산, 데이터 가공 등 LLM이 아닌 처리를 끼워 넣음 |
| **itemgetter(키 추출)** | 입력 딕셔너리에서 **필요한 키의 값만 뽑아** 다음 단계로 전달 |

- **딕셔너리 자동 변환**: 체인 안에 딕셔너리 형태로 쓴 부분은 자동으로 병렬 Runnable로 취급된다.
- **단일 값 입력**: 프롬프트 변수가 하나뿐이면 딕셔너리 없이 **값만** 넘겨도 동작한다.
- **함수 입력 규칙**: 체인 안의 함수는 기본적으로 **입력을 하나** 받는다. 여러 값이 필요하면 딕셔너리로 묶어 받는다.
- **Runnable 데이터 흐름의 핵심**: "입력 딕셔너리를 **분해 → 가공 → 프롬프트 변수로 재조립**"하는 것.

## 12. 관측·추적: LangSmith

- **LangSmith**: LLM 앱의 **실행 과정을 기록·시각화하는 관측(observability) 서비스**.
- 기록되는 것: 프롬프트, 모델 응답, **토큰 사용량, 지연 시간, 오류, 도구 호출 순서** 등.
- **프로젝트 단위**로 실행 기록을 묶어 보며, 켜고 끄는 것은 **설정값(환경변수)**만으로 가능해 코드 수정이 거의 필요 없다.
- 필요한 이유: LLM은 결과가 **비결정적**이고 여러 단계가 얽혀 있어, 어느 단계에서 문제가 생겼는지 **기록 없이는 파악하기 어렵다.**
- 파이썬 표준 로깅(로컬 파일 기록)과는 **목적·범위가 다른 별개의 도구**다.

## 13. 도구(Tool)와 에이전트(Agent)

- **도구(Tool)**: LLM이 호출할 수 있게 **이름·설명·입력 형식을 붙여 둔 함수**(날씨 조회, 검색, 계산 등). 모델은 **설명문을 읽고** 언제 쓸지 판단하므로 설명이 중요하다.
- **에이전트(Agent)**: 모델이 질문을 보고 **도구를 부를지 스스로 결정**하고, 도구 결과를 받아 최종 답을 만드는 구조.
- 동작 흐름: 질문 → (모델 판단) 도구 호출 → 도구 결과 → 모델이 결과를 반영해 **최종 답변**.
- 대화 기록에는 **사용자 질문 → 도구 호출 → 도구 결과 → 최종 답**이 순서대로 쌓인다.
- 일반 LLM 호출과의 차이: LLM이 **자기 지식 밖의 일(실시간 정보, 계산, 외부 시스템)**을 도구로 해결할 수 있다.

## 14. 핵심 요약

1. LLM 앱은 **프롬프트 → 모델 → 출력 처리**의 흐름이며, LCEL이 이를 `|`로 조립한다.
2. **temperature**는 무작위성, **logprob**은 확신도, **토큰**은 비용과 한도의 단위다.
3. 챗 모델은 **역할별 메시지 목록**을 다루고, 멀티모달은 **텍스트+이미지 블록**을 함께 보낸다.
4. 체인은 **한 건(invoke)·스트림(stream)·일괄(batch)·비동기(a~)**로 실행할 수 있다.
5. **Runnable 조합 도구**(Parallel·Passthrough·Lambda·itemgetter)로 분기·병합·가공을 구성한다.
6. 비밀 키는 **`.env`/환경변수**로 관리하고, 실행 과정은 **로깅과 LangSmith**로 추적한다.
7. **도구를 가진 에이전트**는 모델이 스스로 도구 사용 여부를 판단한다.
8. LLM의 출력(특히 이미지 해석·사실 정보)은 **검증이 필요**하다.
