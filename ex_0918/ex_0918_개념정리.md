# ex_0918 개념 정리 (메모리)

코드 설명 없이 **이 폴더에서 등장하는 개념**만 정리한 문서다. (코드별 설명은 [ex_0918_정리.md](ex_0918_정리.md) 참고)

---

## 1. 왜 메모리가 필요한가

- **LLM은 상태가 없다(stateless)**: 매 요청은 독립적이며, 모델은 **이전 대화를 기억하지 못한다.**
- 챗봇이 맥락을 이어 가려면 **이전 대화를 저장해 두었다가 매 요청마다 프롬프트에 다시 넣어 줘야** 한다. 이 "기억 장치"가 **메모리(Memory)**다.
- 기본 흐름: **기록 불러오기 → 프롬프트에 주입 → 모델 답변 → 질문·답변을 기록에 저장**을 매 턴 반복한다.
- **턴(Turn)**: 사용자 발화와 AI 답변의 **한 쌍**.
- 메모리는 결국 **"무엇을 남기고 무엇을 버릴 것인가"의 전략** 문제이며, 종류마다 그 전략이 다르다.

## 2. 메모리 설계의 핵심 문제

| 문제 | 설명 |
|---|---|
| **컨텍스트 윈도우 한도** | 모델이 한 번에 받을 수 있는 토큰 수에는 **상한**이 있다. 대화를 전부 넣으면 결국 넘친다. |
| **비용** | 프롬프트가 길어질수록 **입력 토큰 비용**이 계속 늘어난다. |
| **지연 시간** | 입력이 길수록 응답이 느려진다. |
| **정보 손실** | 줄이려고 버리면 **중요한 정보(예: 사용자 이름)까지 잊을 수** 있다. |
| **관련성** | 오래된 대화 중에는 현재 질문과 무관한 내용이 많다. |

- 메모리 종류는 이 사이의 **절충(trade-off)**을 어떻게 잡느냐에 따라 나뉜다: **정확성 ↔ 비용 ↔ 단순성**.

## 3. 메모리 종류별 개념

### 3.1 전체 저장 (Buffer)

- **모든 대화를 그대로** 쌓는다.
- 장점: 정보 손실이 없고 단순하다.
- 단점: 대화가 길어질수록 **토큰과 비용이 계속 증가**하고, 결국 **컨텍스트 한도를 초과**한다.
- 짧은 대화나 실습에 적합하다.

### 3.2 윈도우 (Window, 최근 k턴)

- **최근 k턴만** 유지하고 오래된 것은 **삭제**한다 (슬라이딩 윈도우).
- k는 **턴 수**이므로 메시지 수는 그 2배(사람+AI)다.
- 장점: 토큰 사용량이 **일정**하고 단순하다.
- 단점: **초반에 나온 중요한 정보를 잊는다.** 삭제된 내용은 복구되지 않는다.

### 3.3 토큰 버퍼 (Token Buffer)

- 턴 수가 아니라 **토큰 수 한도**를 기준으로, 한도를 넘으면 **오래된 메시지부터 삭제**한다.
- **모델의 컨텍스트/비용 한도를 정확히 맞추기에 적합**하다 (긴 답변이 섞여도 총량을 제어).
- 토큰을 세는 데 **해당 모델의 토크나이저**를 쓴다 (답변 생성이 아니라 **계산용**).
- 윈도우와 마찬가지로 삭제된 정보는 복구되지 않는다.

### 3.4 엔티티 메모리 (Entity Memory)

- **엔티티(Entity)**: 대화 속 **사람, 장소, 사물, 날짜, 개념 등 의미 있는 핵심 정보 단위.**
- 대화에서 **엔티티를 추출하고, 엔티티별로 "그에 대해 알려진 사실"을 요약해 저장**한다. 이후 그 엔티티가 언급되면 저장된 정보를 꺼내 쓴다.
- **엔티티 중심**으로 기억하므로 여러 대상이 등장하는 대화에서 유용하다.
- **LLM이 추출을 수행**하기 때문에 추가 호출 비용이 들고, 입력에 오타가 있으면 **잘못된 엔티티**가 생길 수 있다.

### 3.5 지식 그래프 메모리 (Knowledge Graph Memory)

- **지식 그래프**: 정보를 **(주어 – 관계 – 대상)**의 연결(노드와 간선)로 표현한 구조. 예: (Sally – 산다 – 판교).
- 대화에서 **사실(관계)을 추출해 그래프로 저장**하고, 질문에 나온 엔티티와 **연관된 사실만** 꺼내 온다 → 관련 없는 대화가 프롬프트에 들어가지 않는다.
- 한계
  - 내부 프롬프트와 예시가 **영어 중심**이라 한국어에서 관계 추출이 **자주 실패**한다.
  - 매번 LLM을 여러 번 호출해 **느리고 비싸다.**
  - 실무에서는 **거의 쓰이지 않는 실험적 기능**으로 평가된다.

### 3.6 요약 메모리 (Summary Memory)

- 대화 전체를 **LLM이 계속 요약**해 하나의 **요약본**으로 유지한다. 원문은 남기지 않는다.
- 장점: 대화가 아무리 길어도 기록 크기가 **요약 길이 수준**으로 억제된다.
- 단점
  - 요약할 때마다 **LLM 호출**이 발생한다.
  - 요약 과정에서 **세부 정보가 손실**된다.
  - 요약용 내부 프롬프트가 영어라 **한국어 대화도 영어로 요약**될 수 있다.

### 3.7 요약 + 버퍼 (Summary Buffer) — 하이브리드

- **토큰 한도 이내**에서는 **원문을 그대로** 유지하다가, 한도를 넘으면 **오래된 대화는 요약, 최근 대화는 원문**으로 보관한다.
- **가까운 과거는 정확하게, 먼 과거는 압축해서** 보존하므로 **정확성과 비용 절감의 절충안**이다.
- 한도에 도달하기 전에는 요약이 일어나지 않아 **추가 LLM 호출이 없다.**
- 이 챕터의 메모리 중 **가장 실용적**인 방식이다.

### 3.8 벡터 검색 메모리 (Vector Store Retriever Memory)

- 대화를 **임베딩하여 벡터 DB에 저장**하고, 새 질문과 **의미가 비슷한 과거 대화만 검색**해 가져온다.
- **최신순이 아니라 관련성순**으로 기억을 꺼낸다.
- 구성 개념
  - **임베딩(Embedding)**: 텍스트를 **의미를 담은 숫자 벡터**로 바꾼 것. 의미가 비슷하면 벡터가 가깝다.
  - **벡터 저장소(Vector Store)**: 벡터를 저장하고 **가까운 것을 검색**하는 DB (예: FAISS).
  - **유사도 검색 / k**: 질문과 가장 가까운 대화 **k개**를 반환.
  - **인덱스와 거리 측정**: 벡터 간 거리(유클리드/L2 등)로 유사도를 계산한다. **임베딩 차원 수는 사용 모델과 일치**해야 한다.
- 장점: 대화가 아주 길어도 **필요한 부분만** 프롬프트에 넣을 수 있다.
- 단점: 검색이 빗나가면 필요한 맥락이 빠지고, **"방금 한 말"처럼 시간 순서가 중요한 맥락에는 부적합**하다.

## 4. 반환 형식: 문자열 vs 메시지 리스트

| 형식 | 내용 | 어울리는 프롬프트 |
|---|---|---|
| **하나의 긴 문자열** | "Human: ... AI: ..." 텍스트 | 일반 프롬프트 템플릿의 `{history}` 자리 |
| **메시지 객체 리스트** | 사람/AI 메시지의 목록 | 채팅 프롬프트 + **메시지 자리표시자** |

- 챗 모델은 메시지 단위로 입출력하므로 **메시지 리스트 형식이 더 자연스럽다.**
- **메모리 키 이름은 프롬프트의 자리표시자 이름과 일치**해야 기록이 들어간다.
- 메모리가 반환하는 값은 **딕셔너리(키 → 기록)** 형태라서, 체인에 넣을 때는 **필요한 값만 꺼내는 처리**가 필요하다.

## 5. 메모리를 LCEL 체인에 연결하는 개념

- 체인 실행 전에 **메모리에서 기록을 불러와 입력에 덧붙이는 단계**를 넣고, 실행 후에 **질문과 답변을 메모리에 저장**해야 한다.
- 기존 입력을 유지한 채 값을 **추가**하는 Runnable 조합 도구(assign)와, 딕셔너리에서 **값을 꺼내는** 도구를 함께 쓴다.
- 이 과정을 **자동으로 처리해 주는 래퍼**가 "**메시지 기록 관리 Runnable**"이다. 체인을 감싸면 **기록 조회 → 주입 → 저장**을 대신 수행한다.

## 6. 대화 기록 저장소와 세션

### 6.1 세션(Session)과 식별자

- **세션 ID**: **어느 대화인지를 구분하는 키**. 같은 ID끼리는 **같은 대화(같은 기록)**, ID가 다르면 **완전히 새로운 대화**다.
- 다중 사용자 서비스에서는 **사용자 ID + 대화방 ID**의 2단계 식별자를 쓴다. 같은 사용자라도 **대화방이 다르면 별개의 기억**을 갖는다 (새 채팅과 같은 개념).
- 어떤 저장소를 쓸지 결정하는 것은 **"기록을 조회하는 함수"**이며, 실행 시 전달하는 **설정(config)의 식별자 값**으로 대화를 지정한다.
- **설정 가능 필드 명세**: 조회 함수가 받는 식별자들을 프레임워크에 알려 주는 선언 (키 이름, 타입, 설명, 기본값 등).

### 6.2 저장소 방식

| 방식 | 저장 위치 | 지속성 | 용도 |
|---|---|---|---|
| **휘발성(변수/메모리)** | 프로그램 메모리(딕셔너리 등) | 프로그램 종료 시 **사라짐** | 학습, 프로토타입 |
| **영구(데이터베이스)** | DB 파일(SQLite) | **재시작 후에도 유지** | 실제 서비스 |

- **SQLite**: 서버 없이 **파일 하나**로 동작하는 경량 관계형 DB. 대화 기록은 **세션 ID, 메시지** 등을 행으로 저장한다.
- **테이블**: DB에서 데이터를 담는 표. 사용자별로 테이블을 나누는 설계는 가능하지만, **사용자 입력이 그대로 테이블 이름이 되지 않도록 검증**이 필요하다 (보안).
- **데이터베이스에 저장된 대화는 개인정보**를 포함할 수 있으므로, 버전 관리에 올릴 때 주의한다.

## 7. 요약·엔티티·그래프 메모리의 공통 특징: "LLM이 메모리를 관리한다"

- 엔티티 추출, 관계 추출, 요약은 모두 **LLM이 수행**한다. 따라서
  - **추가 호출로 인한 비용·지연**이 발생하고,
  - **LLM의 실수**(잘못된 엔티티, 누락된 관계, 요약 중 정보 손실)가 **메모리 품질**에 그대로 반영되며,
  - 내부 프롬프트가 **영어**라 한국어 처리가 약할 수 있다.
- 반면 **윈도우·토큰 버퍼**는 규칙만으로 동작해 **추가 LLM 호출이 없고 단순**하다.

## 8. 사용 중단(Deprecated)과 현재 권장 방식

- 이 챕터의 **고전적 메모리 클래스**(체인에 붙이던 메모리 객체들)는 **사용 중단 예정(deprecated)**이며, 옛 기능 패키지(classic)로 옮겨졌다.
- 현재 권장: **에이전트(agent) 기반 구성 + 체크포인터(persistence)**를 통한 **단기 기억**, 그리고 **저장소(store)**를 통한 **장기 기억**.
  - **단기 기억(Short-term memory)**: **한 대화(스레드) 안**의 맥락 유지.
  - **장기 기억(Long-term memory)**: **대화를 넘어** 사용자 정보·선호 등을 **영속적으로 보관**.
- **체크포인트(Checkpoint)**: 에이전트 **실행 상태를 저장**해 두었다가 이어서 실행할 수 있게 하는 개념.
- 그럼에도 **"기록을 저장하고 프롬프트에 주입한다"는 원리**는 새 방식에서도 동일하므로, 이 챕터는 **원리 이해용**으로 가치가 있다.

## 9. 개념 한눈에 비교

| 메모리 | 남기는 것 | 토큰 | 정보 손실 | 추가 LLM 호출 |
|---|---|---|---|---|
| 전체 저장 | 전부 | 계속 증가 | 없음 | 없음 |
| 윈도우(k) | 최근 k턴 | 일정 | 오래된 것 삭제 | 없음 |
| 토큰 버퍼 | 한도 내 최근 | 일정 | 오래된 것 삭제 | 없음 |
| 엔티티 | 엔티티별 설명 | 엔티티 수에 비례 | 엔티티 밖 정보 | 있음 |
| 지식 그래프 | 관계(사실) | 관련 사실만 | 추출 실패 시 | 있음 |
| 요약 | 전체 요약 | 요약 크기 | 세부 정보 | 있음 |
| 요약+버퍼 | 요약 + 최근 원문 | 한도 내 | 오래된 세부 | 한도 초과 시만 |
| 벡터 검색 | 관련 있는 것만 | 검색 k개 | 검색 실패 시 | 없음(임베딩만) |

### 선택 기준

| 상황 | 적합한 방식 |
|---|---|
| 짧은 대화, 학습용 | 전체 저장 |
| 최근 맥락만 중요 | 윈도우 / 토큰 버퍼 |
| 길지만 앞부분도 필요 | **요약+버퍼** |
| 방대한 기록에서 관련 부분만 | 벡터 검색 |
| 인물·사물 정보 관리 | 엔티티 |
| 서비스 운영(재시작 후에도 유지) | **DB 기반 저장소** |

## 10. 핵심 요약

1. **LLM은 기억이 없으므로**, 이전 대화를 **저장했다가 프롬프트에 다시 넣어 주는 것**이 메모리의 본질이다.
2. 메모리 설계는 **컨텍스트 한도·비용·지연·정보 손실** 사이의 **절충**이며, 종류마다 "남기고 버리는 방식"이 다르다.
3. **규칙 기반**(전체·윈도우·토큰 버퍼)은 단순하고 빠르지만 **오래된 정보를 잃는다.** **LLM 기반**(엔티티·그래프·요약)은 정보를 압축·구조화하지만 **비용과 오류**가 따른다.
4. **요약+버퍼**는 최근은 원문, 과거는 요약으로 **정확성과 비용을 절충**한 실용적 방식이고, **벡터 검색**은 **관련성** 기준으로 기억을 꺼낸다.
5. 대화는 **세션 ID**로 구분되며, 같은 ID면 같은 기억, 다르면 새 대화다.
6. **휘발성 저장은 종료 시 사라지고**, **DB 저장은 영속적**이다. 저장된 대화는 **개인정보**일 수 있다.
7. 이 챕터의 고전적 메모리 클래스는 **deprecated**이며, 현재는 **에이전트 + 체크포인터(단기) / 스토어(장기)**가 권장된다. 그래도 **원리는 동일**하다.
