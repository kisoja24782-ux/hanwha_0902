# ex_0918 코드 정리 (LangChain 메모리 — CH8)

LLM은 원래 **이전 대화를 기억하지 못한다**. 그래서 챗봇을 만들려면 대화 기록을 따로 저장해 두었다가 매 요청마다 프롬프트에 다시 넣어 줘야 한다. 이 폴더는 **그 "기억" 장치(메모리)를 종류별로** 익히고, 마지막에는 LCEL 체인에 붙이는 방법과 **파일(SQLite)/변수에 저장하는 방법**까지 다룬다.
(체인·LCEL은 [ex_0914 정리](../ex_0914/ex_0914_정리.md), `MessagesPlaceholder`는 [ex_0915 정리](../ex_0915/ex_0915_정리.md) 참고)

## 2. 메모리 공통 사용법

```python
memory.save_context(inputs={"human": "질문"}, outputs={"ai": "답변"})   # 대화 1턴 저장
memory.load_memory_variables({})                                         # 저장된 기록 꺼내기 → {'history': ...}
```

- `save_context(inputs, outputs)`: 사용자 발화와 AI 답변을 **한 쌍(턴)**으로 저장.
- `load_memory_variables({})`: 프롬프트에 넣을 형태로 꺼낸다. 키 이름은 기본 `history` (바꾸려면 `memory_key="chat_history"`).
- 메모리 종류에 따라 **"무엇을 남기고 무엇을 버리는지"만 다르다.** 아래 각 장이 그 차이다.

## 3. ch08_01 — `ConversationBufferMemory` (전부 저장)

```python
from langchain_classic.memory import ConversationBufferMemory

memory = ConversationBufferMemory()
memory.save_context(
    inputs={"human": "안녕하세요, 비대면으로 은행 계좌를 개설하고 싶습니다. 어떻게 시작해야 하나요 ?"},
    outputs={"ai": "안녕하세요! ... 신분증을 준비해 주시겠어요 ?"},
)
memory.load_memory_variables({})["history"]
```

- **모든 대화를 그대로 쌓는다.** 은행 비대면 계좌 개설 시나리오(신분증 → 본인 인증 → 계좌 종류 선택 → 약관 동의 → 완료)로 대화를 계속 추가하면 기록이 계속 길어진다.
- 내부 저장소는 `InMemoryChatMessageHistory` (`chat_memory`).
- 단점: 대화가 길어질수록 **프롬프트가 계속 커져 토큰(비용)이 늘고, 결국 모델의 컨텍스트 한도를 넘는다.** 이후 장의 메모리들은 이 문제를 해결하려는 방법들이다.
- 참고: 첫 번째 `save_context` 결과에 **같은 첫 대화가 두 번** 들어 있다. 그 셀을 두 번 실행했기 때문이다 (셀 재실행 시 메모리가 누적된다는 주의점).

### `return_messages` 옵션

노트북 마크다운 설명을 정리하면:

| 값 | `history`의 형태 | 어울리는 곳 |
|---|---|---|
| `False`(기본) | `"Human: ...\nAI: ..."` **하나의 긴 문자열** | `PromptTemplate`의 `{history}` 자리에 통째로 넣을 때 |
| `True` | `[HumanMessage, AIMessage, ...]` **메시지 객체 리스트** | `ChatPromptTemplate` + `MessagesPlaceholder` (챗 모델은 메시지 단위라 자연스러움) |

## 4. ch08_02 — `ConversationBufferWindowMemory` (최근 k턴만)

```python
memory = ConversationBufferWindowMemory(k=2, return_messages=True)   # 최근 2턴만 유지
# 6턴을 저장했지만...
memory.load_memory_variables({})["history"]
# → 마지막 2턴(사람/AI 각 2개 = 메시지 4개)만 남음
```

- **`k`는 "턴(질문-답변 쌍)"의 수**다. k=2면 메시지는 4개.
- 오래된 대화는 **그냥 버려진다** (요약도 안 함). 결과에는 "정보 입력 완료", "절차 완료" 두 턴만 남고, 앞의 신분증/본인 인증 이야기는 사라졌다.
- 장점: 단순하고 토큰 사용량이 일정. 단점: **초반에 말한 중요한 정보(예: 이름)를 잊는다.**

## 5. ch08_03 — `ConversationTokenBufferMemory` (토큰 한도)

```python
llm = ChatOpenAI(model="gpt-4o-mini")
memory = ConversationTokenBufferMemory(llm=llm, max_token_limit=150, return_messages=True)
```

- 턴 수가 아니라 **토큰 수**를 기준으로 자른다: 총 토큰이 `max_token_limit`(150)을 넘으면 **오래된 메시지부터 제거**.
- `llm`을 넘기는 이유: **토큰을 세는 데 그 모델의 토크나이저를 쓰기 때문**이다 (답변 생성용이 아님).
- 공작 기계 설치 안내 대화를 6턴 저장했더니 **마지막 2턴**("설치 완료 후 안내", "감사합니다")만 남았다. 긴 답변이 섞이면 남는 턴 수는 달라진다.
- 윈도우 메모리보다 **모델 컨텍스트/비용 한도를 정확히 맞추기 좋다.** 마찬가지로 버려진 내용은 복구되지 않는다.

## 6. ch08_04 — `ConversationEntityMemory` (엔티티 메모리)

**"누가/무엇이 어떻다"를 엔티티별로 뽑아 저장**하는 메모리. 엔티티 = 사람, 장소, 사물, 날짜 같은 핵심 정보 단위.

```python
from langchain_classic.chains import ConversationChain
from langchain_classic.memory import ConversationEntityMemory
from langchain_classic.memory.prompt import ENTITY_MEMORY_CONVERSATION_TEMPLATE

conversation = ConversationChain(
    llm=llm,
    prompt=ENTITY_MEMORY_CONVERSATION_TEMPLATE,
    memory=ConversationEntityMemory(llm=llm),
)
conversation.predict(input="테디와 셜리는 한 회사에서 일하는 동료입니다. 테디는 개발자이고 셜리는 디자니어 입니다. 그들은 최근 ... 자신들의 회사를 차릴 계획을 세우고 있습니다.")
conversation.memory.entity_store.store
```

- `ENTITY_MEMORY_CONVERSATION_TEMPLATE`: 엔티티 메모리 전용 프롬프트. 템플릿에 `Context: {entities}` / `Current conversation: {history}` / `Human: {input}` 자리가 있다 (내용은 영어).
- 저장 결과 (`entity_store.store`, 딕셔너리):

```python
{'테디': '테디는 개발자로, 셜리와 함께 ... 회사를 차릴 계획을 세우고 있습니다.',
 '셜리': '셜리는 한 회사에서 일하는 디자이너이며, ...',
 '디자니어': '디자니어는 테디와 함께 회사에서 일하는 동료이며, ...'}
```

- ⚠️ 입력문의 오타 **"디자니어"(디자이너)**를 LLM이 **별개의 인물 엔티티로 잘못 추출**했다. 엔티티 추출도 LLM이 하므로 입력이 부정확하면 이렇게 틀린 엔티티가 생긴다.
- 동작 원리: 매 턴마다 LLM이 ① 엔티티를 추출하고 ② 엔티티별 설명을 갱신한다 → **LLM 호출이 추가로 든다.**
- `ConversationChain`도 deprecated 경고가 나온다. `ConversationTokenBufferMemory`는 import만 하고 쓰지 않았다.

## 7. ch08_05 — `ConversationKGMemory` (지식 그래프 메모리)

대화에서 **(주어, 관계, 대상) 형태의 사실**을 뽑아 그래프로 저장하는 메모리. `networkx`, `langchain-community` 설치가 필요하다.

```python
memory = ConversationKGMemory(llm=llm, return_messages=True)     # llm = gpt-4o
memory.save_context({"input": "Say hi to Sally, she lives in Pangyo"}, {"output": "Who is Sally?"})
memory.save_context({"input": "Sally is a new designer at our company"}, {"output": "Nice to meet her"})

memory.load_memory_variables({"input": "Who is Sally?"})
# {'history': [SystemMessage('On Sally: Sally lives in Pangyo. Sally is a new designer. Sally works at our company.')]}
```

- 질문(`input`)에서 **엔티티(Sally)를 찾아, 그 엔티티에 대해 저장된 사실들만** 돌려준다. → 관련 없는 대화는 안 넣어서 프롬프트가 짧아진다.
- `ConversationChain`에 **직접 만든 프롬프트**를 연결하는 예: `"The AI ONLY uses information contained in the 'Relevant Information' section and does not hallucinate."`처럼 **메모리에 있는 정보만 쓰라**고 지시하고 `{history}` 자리에 지식 그래프 결과를 넣는다.
- 결과: `"My name is Teddy. Shirley is a coworker of mine, and she's a new designer..."` → `'On Shirley: Shirley is a new designer. Shirley works at our company.'`
- 노트북 마크다운의 평가 (그대로 옮기면):
  - 내부 프롬프트와 퓨샷 예시가 **전부 영어**라서 한국어 문장의 관계 추출을 gpt-4o-mini가 자주 실패한다 → 이 셀들은 **영어 문장**으로 실습했고 모델도 `gpt-4o`를 썼다.
  - **실무에서는 거의 안 쓰이는 실험적 기능**이며 매번 LLM을 두 번씩 호출해 느리고 비싸다.

## 8. ch08_06 — 요약 메모리 (`ConversationSummaryMemory`, `ConversationSummaryBufferMemory`)

### 8.1 `ConversationSummaryMemory` — 전체를 요약해서 저장

```python
memory = ConversationSummaryMemory(llm=ChatOpenAI(model="gpt-4o", temperature=0), return_messages=True)
# 유럽 여행 패키지 상담 7턴을 save_context

memory.load_memory_variables({})["history"]
# [SystemMessage("The human asks about the price of a European travel package. The AI responds that ...")]
```

- 대화를 **LLM이 계속 요약**해 하나의 `SystemMessage`로 유지한다. 원문은 남기지 않는다.
- **요약 프롬프트가 영어라 요약본도 영어**로 나왔다 (한국어 대화인데도).
- 대화가 길어져도 기록 크기가 **요약 길이 수준으로 억제**되지만, 턴마다 요약용 LLM 호출이 발생한다.

### 8.2 `ConversationSummaryBufferMemory` — 요약 + 최근 원문 (하이브리드)

```python
memory = ConversationSummaryBufferMemory(llm=llm2, max_token_limit=200, return_messages=True)
```

| 상황 | 결과 |
|---|---|
| 1턴 저장 (200토큰 미만) | **원문 그대로** (`HumanMessage`, `AIMessage`) |
| 5턴 저장 (200토큰 초과) | **오래된 3턴은 요약**(`SystemMessage`) + **최근 2턴은 원문 유지** |

- 노트북 주석 설명: 기준(200토큰)에 도달하기 전까지는 요약하지 않고, 넘으면 **오래된 대화는 요약본으로, 가장 최근 대화는 원본 그대로** 보관한다.
- 최근 대화는 정확하게, 먼 과거는 압축해서 → **정확성과 토큰 절약의 절충**이라 이 챕터에서 가장 실용적인 메모리다.

## 9. ch08_07 — `VectorStoreRetrieverMemory` (벡터 검색 메모리)

대화를 **벡터DB에 저장**하고, 새 질문과 **의미가 비슷한 과거 대화만 검색**해서 가져오는 메모리. 최신순이 아니라 **관련성순**이다.

```python
import faiss
from langchain_classic.docstore import InMemoryDocstore
from langchain_classic.vectorstores import FAISS
from langchain_classic.memory import VectorStoreRetrieverMemory

embeddings_model = OpenAIEmbeddings()
embedding_size = 1536                                   # 임베딩 벡터 차원
index = faiss.IndexFlatL2(embedding_size)               # L2(유클리드) 거리 기반 정확 검색 인덱스
vectorstore = FAISS(embeddings_model, index, InMemoryDocstore({}), {})

retriever = vectorstore.as_retriever(search_kwargs={"k": 1})   # 가장 유사한 1개만
memory = VectorStoreRetrieverMemory(retriever=retriever)
```

- 면접 대화 4턴(자기소개, 프로젝트 역할, 어려움 해결, 강점)을 저장한 뒤:

| 질문 | 반환된 기록 |
|---|---|
| `"면접자 전공은 무엇인가요?"` | **자기소개 턴**(컴퓨터 과학 전공) |
| `"면접자가 프로젝트에서 맡은 역할은 무엇인가요 ?"` | **프로젝트 역할 턴**(백엔드 개발자) |

- 질문마다 **가장 관련된 턴 1개만** 돌아온다. 대화가 아주 길어도 **필요한 부분만 프롬프트에 넣을 수 있다**는 게 장점.
- `k`는 검색할 개수, `embedding_size=1536`은 사용하는 OpenAI 임베딩의 차원 수와 맞춰야 한다.
- 단점: 검색이 빗나가면 필요한 맥락이 빠진다. "방금 한 말" 같은 **시간 순서가 중요한 맥락에는 부적합**하다.
- FAISS는 `%pip install faiss-cpu`로 설치. 이 노트북의 저장소는 메모리(`InMemoryDocstore`)라 **재시작하면 사라진다.**

## 10. ch08_08 — LCEL 체인에 메모리 붙이기 (미완성 노트북)

체인(`prompt | llm`)에서 메모리의 기록을 **프롬프트 변수 `chat_history`로 넣는** 방법을 실습하다 중단된 노트북이다.

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful chatbot"),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "{input}"),
])
memory = ConversationBufferMemory(return_messages=True, memory_key="chat_history")

memory.load_memory_variables({})       # {'chat_history': []}
```

`RunnablePassthrough.assign`으로 입력에 기록을 **덧붙이기**:

```python
runnable = RunnablePassthrough.assign(
    chat_history=RunnableLambda(memory.load_memory_variables) | itemgetter("chat_history")
)
runnable.invoke({"input": "hi"})
# {'input': 'hi', 'chat_history': []}
```

`itemgetter` 없이 쓰면?

```python
runnable = RunnablePassthrough.assign(chat_history=RunnableLambda(memory.load_memory_variables))
runnable.invoke({"input": "hi"})
# {'input': 'hi', 'chat_history': {'chat_history': []}}      ← 딕셔너리가 한 겹 더 감싸짐
```

- `memory.load_memory_variables()`는 `{'chat_history': [...]}` **딕셔너리**를 반환한다. 이걸 그대로 `chat_history`에 넣으면 이중으로 중첩되므로 **`itemgetter("chat_history")`로 리스트만 꺼내야** 프롬프트의 `MessagesPlaceholder`가 정상 동작한다.
- `memory_key`는 **프롬프트의 `MessagesPlaceholder(variable_name=...)`와 반드시 같아야** 한다 (주석: "memory키와 동일하게 입력").
- ⚠️ 마지막 셀 `RunnablePassthrough.assign(chat_history = )`는 **문법 오류가 나는 미완성 코드**다. 모델(`prompt | llm`) 연결과 대화 저장(`save_context`) 단계가 이 노트북에는 없다. (일반적으로는 `runnable | prompt | llm`으로 체인을 만든 뒤 호출하고, 결과를 `memory.save_context`로 저장하는 순서로 이어진다. 이 부분은 노트북에는 없는 내용이다.)
- `ch08_09`/`ch08_10`의 `RunnableWithMessageHistory`가 이 과정을 자동으로 해 주는 더 쉬운 방법이다.

## 11. ch08_09 — SQLite에 대화 저장 (`SQLChatMessageHistory`)

**파일(DB)에 저장**하므로 프로그램을 껐다 켜도 대화가 남는다.

### 11.1 기본 사용

```python
from langchain_community.chat_message_histories import SQLChatMessageHistory

chat_message_history = SQLChatMessageHistory(session_id="sql_history", connection="sqlite:///sqlite.db")
chat_message_history.add_user_message("안녕? 만나서 반가워. 내 이름은 테디야. 나는 랭체인 개발자야. ...")
chat_message_history.add_ai_message("안녕 테디, 만나서 반가워. 나도 잘 부탁해!")
chat_message_history.messages     # [HumanMessage(...), AIMessage(...)]
```

- `connection="sqlite:///sqlite.db"`: 현재 폴더의 `sqlite.db` 파일 (SQLAlchemy 연결 문자열).
- `session_id`: **대화방 식별자**. 같은 ID끼리 같은 대화로 묶인다.
- 테이블 기본 이름은 `message_store` (컬럼: `id`, `session_id`, `message`). `sqlite.db`에서 실제로 확인되는 테이블이다.

### 11.2 체인에 연결 (`RunnableWithMessageHistory`)

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant."),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "{question}"),
])
chain = prompt | ChatOpenAI(model="gpt-4o") | StrOutputParser()

def get_chat_history(user_id, conversation_id):
    return SQLChatMessageHistory(table_name=user_id, session_id=conversation_id, connection="sqlite:///sqlite.db")
```

- **사용자별로 테이블을 나누고(`table_name=user_id`), 대화방별로 세션을 구분(`session_id=conversation_id`)**하는 2단계 구조.

`ConfigurableFieldSpec` — 함수가 받을 인자(`user_id`, `conversation_id`)를 LangChain에 알려 주는 명세

| 인자 | 의미 |
|---|---|
| `id` | 실제로 쓰이는 키 이름 |
| `annotation` | 타입 (`str`) |
| `name`, `description` | 사람이 읽는 이름/설명 (문서용) |
| `default` | 값을 안 줬을 때 기본값 |
| `is_shared` | 여러 단계에서 공유되는 값인지 |

```python
chain_with_history = RunnableWithMessageHistory(
    chain,                                   # 감쌀 체인
    get_chat_history,                        # 기록 저장소를 돌려주는 함수
    input_messages_key="question",           # 입력 딕셔너리에서 사용자 발화가 든 키
    history_messages_key="chat_history",     # 프롬프트에서 기록이 들어갈 자리
    history_factory_config=config_fields,    # 위에서 만든 키 명세
)
```

### 11.3 사용 — `config`로 어느 대화인지 지정

```python
config = {"configurable": {"user_id": "user1", "conversation_id": "conversation1"}}
chain_with_history.invoke({"question": "안녕 반가워, 내 이름은 테디야"}, config)
chain_with_history.invoke({"question": "내 이름이 뭐라고?"}, config)
# → '당신의 이름은 테디라고 하셨죠. 맞나요?'      ← 같은 대화방이라 기억함

config2 = {"configurable": {"user_id": "user1", "conversation_id": "conversation2"}}
chain_with_history.invoke({"question": "내 이름이 뭐라고?"}, config2)
# → '죄송하지만, 제가 당신의 이름을 알 수 있는 방법이 없습니다...'   ← 다른 대화방이라 모름
```

- 같은 사용자라도 **`conversation_id`가 다르면 별개의 대화**다. 챗봇의 "새 채팅"에 해당한다.
- `sqlite.db`에는 `user1` 테이블이 생겼고 8행이 저장되어 있다.
- 주의: **`user_id`를 그대로 SQL 테이블 이름으로 쓰는 구조**라서, 사용자 입력이 그대로 들어가는 서비스에서는 이름 검증(허용 문자 제한 등)이나 다른 방식(단일 테이블 + 사용자 컬럼)을 고려해야 한다.

## 12. ch08_10 — 휘발성 메모리 (파이썬 dict에 저장)

DB 없이 **변수에만** 저장하므로, 프로그램/커널이 끝나면 사라진다. 가장 단순한 구현.

```python
from langchain_community.chat_message_histories import ChatMessageHistory

store = {}                                             # 세션ID → 대화 기록

def get_session_history(session_ids):
    print(f"[대화 세션ID]: {session_ids}")
    if session_ids not in store:
        store[session_ids] = ChatMessageHistory()      # 처음 보는 세션이면 새로 생성
    return store[session_ids]

chain_with_history = RunnableWithMessageHistory(
    chain, get_session_history,
    input_messages_key="question",
    history_messages_key="chat_history",
)

chain_with_history.invoke({"question": "나의 이름은 테디입니다."}, config={"configurable": {"session_id": "abc123"}})
```

- 프롬프트의 주석: **`chat_history` 키 이름은 가급적 바꾸지 말 것** (`RunnableWithMessageHistory`의 `history_messages_key`와 짝이 맞아야 하므로).
- `config={"configurable": {"session_id": ...}}`: **기본 설정에서는 `session_id` 하나만** 넘기면 된다. (ch08_09에서 `user_id` + `conversation_id` 두 개를 쓰려면 `ConfigurableFieldSpec`이 필요했다.)
- 이 노트북의 세 호출은 세션 ID가 `abc123`, `abc1234`, `abcd1234`로 **전부 다르다**. 그래서 마지막 `"내 이름이 뭐라고 했지?"`(`abcd1234`)에 `"이전 대화 내용을 확인할 수 없어서..."`라고 답했다. 이름을 알려준 세션(`abc123`)에 다시 물으면 기억할 것이다 (코드 구조상). ID가 비슷해서 헷갈리기 쉬우니 실습할 땐 **같은 ID / 다른 ID를 구분해서** 비교해 보자.
- 호출마다 출력되는 `[대화 세션ID]: ...`는 `get_session_history`의 `print`이며, 어떤 세션이 조회되는지 확인하는 디버깅용이다.

### ch08_09 vs ch08_10 비교

| | ch08_09 (SQLite) | ch08_10 (dict) |
|---|---|---|
| 저장소 | `SQLChatMessageHistory` | `ChatMessageHistory` |
| 영속성 | **파일에 남음** | 프로세스 종료 시 사라짐 |
| 식별자 | `user_id` + `conversation_id` | `session_id` 하나 |
| 추가 설정 | `ConfigurableFieldSpec` 필요 | 불필요 |
| 용도 | 실제 서비스 | 프로토타입/학습 |

## 13. 개념 한 장 요약

### 메모리 종류 선택

| 메모리 | 남기는 것 | 토큰 증가 | 정보 손실 | 추가 LLM 호출 |
|---|---|---|---|---|
| Buffer | 전부 | 계속 증가 | 없음 | 없음 |
| BufferWindow (k) | 최근 k턴 | 일정 | 오래된 건 삭제 | 없음 |
| TokenBuffer | 토큰 한도 내 최근 | 일정 | 오래된 건 삭제 | 없음 (토큰 세기만) |
| Entity | 엔티티별 설명 | 엔티티 수에 비례 | 엔티티 밖 정보 | 있음 |
| KG | 관계 그래프 | 관련 사실만 | 추출 실패 시 | 있음 (2회) |
| Summary | 전체 요약 | 요약 크기 | 세부 정보 | 있음 |
| SummaryBuffer | 요약 + 최근 원문 | 한도 내 | 오래된 세부 | 넘칠 때만 |
| VectorStoreRetriever | 관련 있는 것만 | 검색 k개 | 검색 실패 시 | 없음 (임베딩만) |

### 대화 기록 흐름 (원리)

```
사용자 질문 ─▶ [기록 불러오기] ─▶ prompt(system + chat_history + human) ─▶ LLM ─▶ 답변
                    ▲                                                          │
                    └──────────── [질문/답변 저장] ◀────────────────────────────┘
```

### 저장소 선택

| 목적 | 방식 |
|---|---|
| 학습/프로토타입 | `ChatMessageHistory` + dict (ch08_10) |
| 영구 저장 | `SQLChatMessageHistory` (ch08_09) |
| 최신 권장 | `create_agent` + LangGraph 체크포인터 |

## 14. 공부하며 기억할 함정

1. **앞부분 메모리 클래스는 모두 deprecated**다. 원리 학습용으로 보고, 새 코드는 LangGraph persistence(체크포인터)를 쓴다.
2. 메모리 안에 든 것은 **셀을 다시 실행하면 누적**된다 (ch08_01에서 첫 대화가 두 번 저장됨). 초기화하려면 객체를 다시 만든다.
3. Window의 `k`는 **턴 수**이고 메시지 수는 2배다. TokenBuffer의 `llm`은 **토큰 계산용**이다.
4. Entity/KG/Summary는 **LLM을 추가로 호출**하므로 느리고 비용이 든다. 입력에 오타가 있으면 엔티티가 잘못 만들어진다 (`디자니어`).
5. KG·Summary 메모리의 내부 프롬프트는 **영어**다. 한국어로 쓰면 요약이 영어로 나오거나 추출이 부정확해진다.
6. `memory_key`와 프롬프트의 `MessagesPlaceholder` 이름(`chat_history`)이 다르면 기록이 안 들어간다. `load_memory_variables`의 결과는 **딕셔너리**이므로 필요하면 `itemgetter`로 꺼낸다.
7. 대화를 기억하게 하려면 **같은 `session_id`(또는 `user_id`+`conversation_id`)**를 써야 한다. ID가 다르면 새 대화가 된다.
8. dict 저장(`ch08_10`)은 재시작하면 사라지고, SQLite 저장은 `sqlite.db`에 남는다. 이 DB에는 대화 내용이 그대로 들어 있으니 **Git에 올리기 전에 포함 여부를 확인**하자.
9. `ch08_08`은 **미완성**(마지막 셀이 문법 오류)이다. 이 부분은 직접 이어서 완성해 보면 좋은 연습이다.
