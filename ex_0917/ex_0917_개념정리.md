# ex_0917 개념 정리 (모델 활용)

코드 설명 없이 **이 폴더에서 등장하는 개념**만 정리한 문서다. (코드별 설명은 [ex_0917_정리.md](ex_0917_정리.md) 참고)

## 1. 다양한 LLM을 쓰는 이유와 추상화

- LLM 제공자는 여러 곳이다: **OpenAI, Anthropic(Claude), Google(Gemini)** 같은 클라우드 API와, 내 컴퓨터에서 직접 돌리는 **로컬 모델**.
- 필요한 이유: 성능·가격·데이터 보안·사용 제한이 서로 다르므로, 상황에 맞게 **모델을 교체**할 수 있어야 한다.
- **모델 추상화**: LangChain은 제공자마다 다른 호출 방식을 **같은 인터페이스**(호출/스트리밍/배치)로 감싼다. 그래서 체인의 나머지는 두고 **모델 부분만 바꿔 끼우면** 된다.
- 다만 **응답의 세부 형식, 지원 기능, 입력 규칙은 제공자마다 다르다.** 추상화가 모든 차이를 없애 주지는 않는다.

## 2. 클라우드 API 모델 vs 로컬 모델

| 기준 | 클라우드 API | 로컬 모델 |
|---|---|---|
| 실행 위치 | 제공자의 서버 | **내 컴퓨터** |
| 성능 | 일반적으로 높음 | 모델 크기·PC 사양에 좌우, 소형은 낮음 |
| 비용 | **사용량(토큰) 기반 과금** | 사용료 없음 (장비·전기 비용) |
| 개인정보 | 데이터가 **외부 서버로 전송**됨 | **PC 밖으로 나가지 않음** |
| 준비 | API 키, 결제(크레딧) | 모델 파일 다운로드, 실행 환경 구성 |
| 결과 안정성 | 높음 | 지시 이행·형식 준수가 불안정할 수 있음 |

- **크레딧/과금**: 클라우드 모델은 잔액이 없으면 호출이 되지 않는다. 키가 있어도 **결제 상태**를 확인해야 한다.
- 로컬 모델은 **보안이 중요하거나 비용을 줄이고 싶을 때** 선택하지만, **결과 품질과 정확성을 따로 검증**해야 한다.

## 3. 캐싱(Caching)

- **캐싱**: 같은 요청에 대한 **결과를 저장해 두고, 다시 요청이 오면 저장된 결과를 즉시 반환**하는 기법.
- 효과
  - **속도**: 네트워크·생성 시간이 사라져 **수 초 → 수 밀리초**로 단축
  - **비용**: 캐시가 적중한 호출은 **API 호출이 발생하지 않아 비용이 없다**
  - **재현성**: 같은 입력에 같은 답을 돌려줌 (개발·테스트 시 유용)
- **캐시 적중(hit) / 미스(miss)**: 저장된 결과가 있으면 적중, 없으면 실제 호출 후 저장.
- **캐시 키**: **같은 프롬프트 + 같은 모델 설정**일 때만 적중한다. 문장이 한 글자만 달라도 새 호출이 된다.
- **전역 설정**: 캐시는 체인마다가 아니라 **애플리케이션 전체에 적용**되는 설정이다.
- 캐시를 **교체하면 새 캐시는 비어 있어** 첫 호출은 다시 실제 호출이 된다.

### 저장 방식

| 방식 | 저장 위치 | 지속성 | 용도 |
|---|---|---|---|
| **인메모리 캐시** | 프로그램 메모리 | 프로그램 종료 시 **사라짐** | 짧은 실험 |
| **SQLite 캐시** | **디스크의 파일**(DB) | 재시작해도 **유지됨** | 개발 중 반복 실행, 비용 절감 |

- **SQLite**: 별도 서버 없이 **파일 하나로 동작하는 경량 데이터베이스**.
- 캐시는 **동일 입력에 동일 출력이 허용되는 경우**에만 적합하다. 매번 다른 답(창의적 생성)이 필요한 곳에서는 부적합하다.

## 4. 직렬화와 역직렬화 (Serialization)

- **직렬화**: 메모리 속 객체를 **저장·전송할 수 있는 데이터(파일/문자열)로 변환**하는 것.
- **역직렬화**: 저장된 데이터를 읽어 **원래의 객체로 복원**하는 것.
- 필요한 이유: 체인 구성을 **파일로 저장해 재사용·공유·버전 관리**하기 위해.
- **저장되는 것은 "객체 자체"가 아니라 "설계도(생성 명세)"**: 어떤 클래스를 어떤 설정값으로 만들지에 대한 정보다. 복원 시 이 명세대로 객체를 **다시 생성**한다.
- **비밀 값(API 키)은 저장되지 않는다.** 값 대신 **"이 이름의 비밀을 가져와라"는 참조**만 남으므로, 파일이 유출돼도 키는 새지 않는다. 복원할 때 환경변수나 직접 전달로 **키를 다시 공급**한다.
- **직렬화 가능 여부**: 모든 객체가 저장 가능한 것은 아니다. **사용자 정의 함수 등이 낀 체인은 직렬화가 안 될 수 있다.**

### 저장 형식

| 형식 | 특징 |
|---|---|
| **JSON** | 텍스트, 사람이 읽기 쉬움, **언어·환경에 독립적**, 상대적으로 안전 |
| **Pickle** | 파이썬 전용 **바이너리** 형식, 복잡한 객체도 저장 가능 |

### 보안 개념

- **Pickle은 파일 내용에 따라 임의 코드가 실행될 수 있다.** 출처를 모르는 pickle 파일은 **절대 열면 안 된다.** 단순 데이터라면 JSON이 더 안전하다.
- **복원 허용 범위**: 아무 클래스나 복원하게 두면 악의적 파일이 **임의 코드 실행**으로 이어질 수 있다. 그래서 기본은 **핵심(core) 클래스만 허용**하고, 외부 패키지 클래스는 **명시적으로 허용**해야 한다.
- 원칙: **신뢰할 수 있는 출처의 파일만 복원**한다.

## 5. 토큰 사용량과 비용 추적

- **토큰 기반 과금**: 클라우드 모델은 **입력 토큰과 출력 토큰의 수**에 따라 비용이 든다. 보통 **출력 토큰 단가가 입력보다 비싸다.**
- **추적 대상**: 총 토큰, 입력(프롬프트) 토큰, 출력(답변) 토큰, 요청 수, 누적 비용.
- **콜백(Callback)**: 실행 중 **특정 시점에 자동으로 호출되는 관찰자**. 여기서는 "호출이 끝날 때마다 사용량을 집계하는 장치"로 쓰인다.
- **컨텍스트 매니저(with 블록)** 방식: **지정한 구간 안의 모든 호출을 합산**하고, 구간을 벗어나면 집계가 멈춘다.
- **제공자 한정**: 이런 추적 기능은 **특정 제공자(OpenAI) 전용**이다. 다른 제공자는 응답 메타데이터의 사용량 정보를 직접 확인해야 한다.
- **비용 = 입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가.** 단가는 **모델·시점에 따라 바뀌므로** 계산값은 참고용이다.
- **캐싱과의 관계**: 캐시가 적중한 호출은 토큰이 소모되지 않는다. 캐싱 + 추적으로 **비용을 측정하고 줄일 수 있다.**

## 6. 응답 형식의 차이: 콘텐츠 블록

- 일부 모델(예: 최신 Gemini)은 응답을 **문자열 하나가 아니라 "블록의 리스트"**로 준다. 블록에는 **텍스트, 추론(thinking) 과정, 서명** 등이 **종류별로** 들어 있다.
- **추론(Thinking)**: 모델이 답하기 전에 거치는 **내부 사고 과정**. 최종 답과 **분리되어** 제공되기도 한다.
- 영향: 응답을 **문자열이라고 가정한 도구**는 오류가 난다.
- 해결 개념: 블록에서 **텍스트 종류만 골라내는 처리**(문자열 파서 등)를 응답 뒤에 붙이거나, 블록을 순회하며 **type이 텍스트인 것만** 사용한다.
- 교훈: **모델을 바꾸면 응답 구조가 달라질 수 있다.**

## 7. 안전 설정(Safety Settings)

- **안전 설정**: 모델이 **유해 콘텐츠를 어느 강도로 차단할지** 정하는 옵션. 유해 유형(성적, 혐오, 괴롭힘, 위험 행위 등)별로 **차단 임계값**을 설정한다.
- **차단 없음(BLOCK_NONE)**부터 **엄격한 차단**까지 단계가 있다.
- **인자 이름 오타의 위험**: 설정 이름을 틀리면 오류가 아니라 **경고만 나오고 설정이 무시**되는 경우가 있다. 경고 메시지를 반드시 읽어야 한다.
- 안전 설정을 완화한다고 모델이 무엇이든 답하는 것은 아니다. **제공자의 기본 정책은 별도로 적용**된다.

## 8. 멀티모달 (모델별 차이)

- **멀티모달 모델**: 텍스트와 함께 **이미지 등을 입력**받는 모델. 클라우드(Gemini 등)와 로컬(llava 등) 모두 있다.
- 로컬 이미지는 **base64 문자열(data URL)**로 변환해 전달한다.
- **이미지 입력 형식은 제공자마다 조금씩 다르다** (구조·필드 형태).
- 프롬프트의 **언어에 따라 답변 언어도 달라진다** (영어로 물으면 영어로 답함).
- **역할 지정**(예: 시인)과 함께 이미지를 주면 이미지 기반 **창작**도 가능하다.

## 9. 로컬 LLM

### 9.1 개념

- **로컬 LLM**: 인터넷 API 없이 **내 PC에서 직접 실행**하는 모델. 오픈소스/오픈 웨이트 모델(Gemma, EEVE-Korean, llava 등)이 대상이다.
- 장점: **비용 없음, 데이터 외부 유출 없음, 오프라인 사용, 자유로운 커스터마이징.**
- 단점: **하드웨어(메모리·GPU) 요구**, 소형 모델의 낮은 성능·불안정한 형식 준수, **최신 사실 지식·정확성 부족**.

### 9.2 모델 파일과 양자화

- **GGUF**: 로컬 실행용으로 만든 **모델 파일 형식**. 한 파일에 모델 가중치가 들어 있다.
- **양자화(Quantization)**: 모델의 **숫자 정밀도를 낮춰(예: 4비트)** 파일 크기와 메모리 사용량을 줄이는 기법. **품질은 조금 손해 보고 실행 가능성을 얻는 절충**이다. (파일명의 `Q4` 같은 표기가 이를 의미)
- **파라미터 수(예: 7B, 10.8B)**: 모델의 크기 지표. 클수록 성능이 좋지만 **더 많은 자원**이 든다.
- **한국어 특화 모델**: 영어 중심 모델보다 한국어 답변 품질이 좋다 (영어 질문에도 한국어로 답하기도 함).

### 9.3 Ollama

- **Ollama**: 로컬 모델을 **내려받고 실행·관리해 주는 도구**. 모델을 이름으로 불러 쓸 수 있게 해 준다.
- **Modelfile**: Ollama용 **모델 정의 파일**. 베이스 모델, 프롬프트 형식, 정지 토큰 등을 지정해 **커스텀 모델로 등록**한다.
- **JSON 모드**: 출력을 **유효한 JSON으로 제한**하는 옵션. 형식은 지키지만 **지시의 의미를 오해**할 수 있다.

### 9.4 GPT4All

- 로컬에서 모델 파일을 직접 불러 실행하는 또 다른 도구. **GPU 사용 여부**를 지정할 수 있다.
- **LLM 클래스 vs Chat 클래스**: 문자열 입출력 방식의 모델과 메시지 입출력 방식의 모델은 **입출력 타입이 다르다.**

### 9.5 프롬프트 형식(Chat Template)과 정지 토큰

- 모델은 **학습할 때 쓴 대화 형식**(역할 표시, 특수 토큰의 배치)이 있고, 그 형식에 맞춰야 **정상적인 답변**을 한다.
- **채팅 템플릿**: 시스템/사용자/AI 발화를 **모델이 학습한 표기**로 감싸는 틀. Ollama는 Modelfile에서, GPT4All 등은 **프롬프트 문자열에 직접** 적용한다.
- **특수 토큰(`<s>`, `</s>` 등)**: 발화의 시작과 끝을 표시하는 표식.
- **정지 토큰(Stop token)**: 이 토큰이 나오면 **생성을 멈추도록 하는 지정**. 지정하지 않으면 종료 표식이 **결과 텍스트에 섞여 출력**된다.

## 10. 스트리밍 출력과 콜백

- **스트리밍 콜백**: 토큰이 생성되는 즉시 **화면에 내보내는 처리기**. 응답을 한 번에 받는 호출이더라도 **실시간으로 출력되는 것처럼** 보이게 한다.
- 스트리밍을 **반복문으로 직접 순회**하는 방식과 **콜백으로 자동 출력**하는 방식이 있다.

## 11. 개념 한눈에 비교

### 모델 선택 기준

| 상황 | 고려할 선택 |
|---|---|
| 최고 품질이 필요 | 클라우드 API 모델 |
| 민감한 데이터를 다룸 | **로컬 모델** |
| 비용을 줄이고 싶음 | 로컬 모델, 또는 **캐싱** |
| 이미지 이해가 필요 | 멀티모달 모델 (클라우드/로컬 모두 가능) |
| 형식이 엄격한 출력 | 큰 모델 + 구조화 출력 (소형 로컬은 검증 필수) |

### 저장 관련 기능

| 기능 | 저장 대상 | 핵심 |
|---|---|---|
| 캐싱 | LLM의 **응답** | 속도·비용 절감, 동일 입력에서만 적중 |
| 직렬화 | 체인의 **구성(설계도)** | 재사용·공유, **키는 저장 안 됨** |

### 응답 형식

| 유형 | 형태 |
|---|---|
| 일반 모델 | 문자열 |
| 블록형 응답 모델 | 블록 리스트 (텍스트/추론/서명 등) |

## 12. 핵심 요약

1. LangChain의 **모델 추상화** 덕분에 모델만 바꿔 끼울 수 있지만, **응답 구조·기능·입력 형식은 제공자마다 다르다.**
2. **클라우드 모델**은 성능이 높고 **과금**이 있으며, **로컬 모델**은 무료·보안에 유리하지만 성능·안정성이 낮을 수 있다.
3. **캐싱**은 동일 요청의 결과를 저장해 **속도와 비용을 줄인다.** 인메모리는 휘발성, SQLite는 **영속적**이다.
4. **직렬화**는 체인의 **설계도**를 저장하며 **API 키는 저장되지 않는다.** **Pickle은 출처를 모르면 열지 않는다.**
5. 복원은 **허용 범위를 명시**해야 하며, 신뢰할 수 있는 파일만 다룬다.
6. **토큰·비용 추적**은 `with` 구간의 호출을 합산하며, **제공자 전용**이다.
7. 일부 모델은 응답이 **블록 리스트**로 오므로 텍스트만 추출하는 처리가 필요하다. **인자 이름 오타**는 조용히 무시될 수 있다.
8. 로컬 모델은 **양자화된 GGUF 파일 + 학습된 대화 형식(채팅 템플릿) + 정지 토큰**을 맞춰야 정상 동작하며, **결과는 항상 검증**한다.
